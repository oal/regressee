# Foundation shell — development proposal

Mode: Operate. Native desktop GPUI, never a webview. Human visual review is
pending; the Phase 0 bench was inspected as an anti-reference, not approval.
Its latest owned-window capture is entirely black, so source tokens and the
documented bench are the only incumbent visual context available.

## Direction contract

**THESIS:** a release manager's readiness checklist: make the next safe action
obvious and keep saved settings separate from captured evidence. Refuse the
developer dashboard of fabricated counts and charts.

**OWN-WORLD:** cool light working surface, deep ink, restrained teal action and
selection, system UI sans, compact squared-off controls with small radii;
horizontal rules organize information rather than floating card stacks.

**STORY:** choose a project, save website settings, reopen them, then understand
which capture capabilities are not built yet. No invented runs or green verdicts.

**FIRST VIEWPORT:** 204px navigation rail, generous 32px working inset, 28px screen
heading, one right-aligned create action, full-width project rows. Setup replaces
the list with labeled name/address inputs and one save action. Results pairs a
plain coverage explanation with an honest empty evidence field, not fake images.

**FORM:** candidate 5, readiness checklist, seed `2909835a`. Grounded alternatives
were (1) file library, (2) print contact sheet, (3) calendar release book,
(4) document inspector, (5) readiness checklist, (6) deployment handover board,
(7) annotation tray. The seed assignment is acknowledged as the proposal, not a
human choice. Category conventions are subordinate to native task clarity.

**FINISH:** unreviewed and undocumented is unfinished; this build ends with the finish review, the verdict, DESIGN.md, and every shipping raster carrying its provenance

## Design scope and review boundary

No approval is required to implement the explicitly authorized local proposal;
human confirmation of setup/results is a separate open acceptance gate. The
structured question tool was actually searched and is unavailable in this
harness. Do not silently call this user-approved. No parallel reviewer/documenter
is spawned: the user requires a subsequent independent verifier, strictly serial.
No shipping rasters are used. Native UI inspection is one batched attempt, with
at most one confirmation, never repeated black-window loops.

Seed challengers, evaluated against identification / clarity respectively:

| --- | --- | --- |

| Character catalog → project roster | declined / declined | Each project has a legible identity and selection state, no mascots |
| Design annual → screenshot plates | competitive / declined | Untinted evidence gets the largest future viewing surface |

## Screen topology and future flow sketches (not implementations)

- **Projects:** actual stored project rows → open setup. Create starts an inline
  form. Rows state “No captures yet,” not a made-up last check.
- **Project setup:** name/address save works now; future addresses → scope →
  screen sizes → login/consent → Find pages → discovery preview → confirmation →
  capture coverage → Save baseline. Editing preserves other stored settings.
- **Results:** honest empty state now; future changed-first queue → comparison
  viewer → sensitivity/mask revision → review decision → explicit acceptance.
- **History:** no runs or baselines now; future baseline/run list → impact preview
  → explicit delete, restore or export. Nothing auto-deletes history.
- **Settings:** actual paths/storage totals; runtime explicitly not configured.
  The original folder-picker demo did not inspect files; it was removed on
  2026-10-15. Current settings disclose actual storage locations without a picker.
- **Sharing, later:** selected baseline → privacy/coverage preview → ZIP export;
  import as new project → separate environment/login → fixed-target check.

Vocabulary follows PLAN §3. “Baseline” means approved reference screenshots.
“Screen sizes” describes capture profiles, not real devices. “Changed” is not
“defective”; “Could not capture” is never “No significant change.”

## Phase 2 extension — inherited proposal, not human approval

The original foundation concept and tokens above remain unchanged. Phase 2
replaces the former Results/setup placeholders with actual one-target services:
save settings → capture → inspect coverage/warnings → explicit Save baseline
confirmation → separate check → synchronized before/after/diff. The next safe
action sits above untinted evidence panes; status words distinguish changed,
unchanged, failed, cancelled, interrupted and pending analysis. One shared
zoom/pan position controls bounded 512-row tiles; full originals are not textures.

Settings exposes actual trusted setup/repair and discloses missing configuration
or development-only scope. There are no invented crawl counts or demo outcomes.
Backend/simulated action checks passed; the single native Phase 2 inspection
remained unmapped, so composition, typography, native input, accessibility and
human visual approval remain open. See `docs/phases/02-status.md`. The subsequent
independent verifier owns rendered review; no finish/human verdict is invented.
